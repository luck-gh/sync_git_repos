# sync_git_repos

批量同步本地 git 仓库的命令行工具，Windows / Linux / macOS 通用。

递归扫描一个目录下的所有 git 仓库，并行 `fetch`，对比每个仓库本地分支与 `origin` / `upstream` 的领先/落后关系，先给出一张状态表和操作建议，确认后再统一执行拉取或推送。

## 特性

- **一次扫一整个目录**：递归查找所有含 `.git` 的仓库，自动跳过 `node_modules`、`.venv`、`__pycache__` 等目录。
- **并行 fetch + 进度条**：`fetch` 是网络 IO，默认用 8 个线程并发，总耗时约等于最慢的那个仓库，而不是所有仓库之和；检查阶段带实时进度条。
- **卡住的仓库不拖累全局**：所有 git 网络操作都禁用交互式等待（缺凭证 / 未确认 host key 会直接失败而非挂起），并对 `fetch` / `push` 设了超时；某个仓库卡住会被跳过并记录原因，其他仓库照常进行。
- **先检查再执行**：阶段一只做只读的 `fetch` 和分析，输出状态表；阶段二才动手，且默认需要人工确认。
- **同时支持 origin 和 upstream**：fork 场景下能识别 `upstream`，并可在同步 upstream 后自动推回 `origin`，让 GitHub 上的 fork 也保持最新。
- **安全默认 + 强制模式**：默认遇到脏工作区或远程分叉会跳过、不动现场；加 `--force` 才会自动 stash、自动合并。
- **冲突可控**：强制模式下遇到冲突时保留本地版本、跳过远程改动，并在结果里列出具体文件名，方便事后手动处理。
- **自动写日志**：执行结果会写入 `logs/` 目录，带时间戳。

## 依赖

- Python 3.10+（用到了 `str | None` 等语法）
- 系统能在命令行直接调用 `git`（即 `git` 已在 PATH 中）

无第三方包依赖，只用标准库。

## 快速开始

```bash
# 检查 D:\code 下所有仓库，确认后拉取(默认,安全模式)
python sync_git_repos.py D:\code

# 不传目录则默认扫描当前目录
python sync_git_repos.py
```

先看输出的状态表和建议，确认无误后输入 `y` 执行。

## 用法

```
python sync_git_repos.py <扫描目录> [选项]
```

### 常用示例

```bash
python sync_git_repos.py D:\code                      # 检查 + 确认后拉取(默认,安全模式)
python sync_git_repos.py D:\code --mode push          # 检查 + 确认后推送
python sync_git_repos.py D:\code --force              # 强制拉取,脏工作区/冲突也尝试处理
python sync_git_repos.py D:\code --mode push --force  # 强制推送(含分叉自动合并后推送)
python sync_git_repos.py D:\code --dry-run            # 只打印会执行的命令,不实际跑
python sync_git_repos.py D:\code --yes                # 跳过确认提示,直接执行
python sync_git_repos.py D:\code --workers 16         # 仓库很多时调大并发线程数
python sync_git_repos.py D:\code --timeout 15         # fetch/push 超过 15s 就跳过
python sync_git_repos.py D:\code --timeout 0          # 网络操作不超时，一直等待
```

### 选项说明

| 选项 | 默认值 | 说明 |
|------|--------|------|
| `base_dir` | `.`（当前目录） | 要扫描的根目录 |
| `--mode {pull,push}` | `pull` | 集体拉取还是集体推送 |
| `--dry-run` | 关 | 只打印将执行的操作，不实际运行 merge / push / stash |
| `--yes` / `-y` | 关 | 跳过确认提示，检查完直接执行 |
| `--force` / `-f` | 关 | 强制模式，详见下文 |
| `--push-after-upstream-sync` | 关 | pull 模式下，合并完 upstream 后若本地领先 origin，自动推回 origin |
| `--workers N` | `8` | 并行 fetch 的线程数，仓库多时可调大；设为 `0` 关闭多线程，改用单线程串行 |
| `--timeout SEC` | `30` | 单个仓库 fetch/push 的最长等待秒数，超时则跳过；设为 `0` 时不超时、一直等待 |
| `--log-dir DIR` | 脚本目录下的 `logs/` | 执行日志输出目录 |

## 工作流程

### 阶段一：检查（只读）

对所有含 `origin` 的仓库并行执行 `fetch`（有 `upstream` 的一并 fetch），然后对比本地分支与远程的 ahead / behind 关系，输出一张状态表：

```
================ 检查结果 ================
仓库                            分支          origin(落后/领先)   upstream(落后/领先)  建议
--- 需要拉取/同步 upstream ---
my-project                     main         3/0                无 upstream          建议拉取 origin (落后 3)
--- 需要推送 ---
another-repo                   dev          0/2                无 upstream          建议推送 origin (领先 2)
--- 无需操作 ---
...
```

`origin(落后/领先)` 中，**落后** = 远程有本地没有的提交数（需要拉取），**领先** = 本地有远程没有的提交数（需要推送）。

仓库会按需要关注的程度分组排序：fetch 超时 > 分叉 > 需推送 > 需拉取 > 仅工作区不干净 > 无需操作 > 跳过。

### 阶段二：执行（需确认）

列出需要操作的仓库，输入 `y` 后统一执行（或用 `--yes` 跳过确认）。

- **`--mode pull`（默认）**：对建议"拉取"的仓库执行 merge；有 upstream 且落后时也会同步 upstream。
- **`--mode push`**：对建议"推送"的仓库执行 `git push origin <branch>`。

## 安全模式 vs 强制模式

### 默认（不加 `--force`）——安全优先，不动现场

- 工作区不干净 → **跳过该仓库**
- 远程分叉（本地和远程都有对方没有的提交）→ **跳过**，只提示需手动处理

### 加 `--force` 后——尽量自动处理

- 工作区不干净 → 自动 `git stash` 暂存本地改动，操作完成后 `stash pop` 恢复。若恢复时和刚拉取的内容冲突，冲突文件**保留本地改动**（stash 内容），其余文件正常应用。
- 合并遇到冲突（远程分叉）→ 冲突文件**保留本地版本**（跳过该文件的远程改动），非冲突文件正常合并，仍会完成一次合并提交。
- push 遇到分叉 → 先按上述规则合并 remote 变更（冲突文件保留本地版本），合并完成后再推送。

> ⚠️ **注意**：强制模式下任何"跳过冲突文件"都会在结果里列出具体文件名。因为这些文件的远程改动被跳过了、不会以冲突标记留在工作区里，建议事后手动检查这些文件是否需要单独合入远程的改动。

## 执行结果与日志

执行完输出一张结果表，状态含义：

| 状态 | 含义 |
|------|------|
| `OK` | 正常完成 |
| `CONFLICT_RESOLVED` | 完成，但有冲突文件按"保留本地"规则处理过 |
| `SKIP` | 被跳过（脏工作区 / 分叉，且未加 --force） |
| `NOTHING` | 无需操作 |
| `FAILED` | 失败（详情见结果表里的说明） |

同一份结果会写入日志文件：

```
logs/sync-repos-<mode>-<时间戳>.log
```

## 仓库卡住 / fetch 迟迟不动怎么办

检查阶段进度条停在 `18/20` 这类中间值不动，通常是某个仓库的 `git fetch` 挂住了。本工具已从两方面兜底，让卡住的仓库不拖累其他仓库：

- **禁用交互式等待**：所有 git 网络操作都设了 `GIT_TERMINAL_PROMPT=0`、`GCM_INTERACTIVE=Never` 和 `ssh -oBatchMode=yes`。缺少凭证、密码或未确认 host key 时会**直接失败**，而不是卡在那里等你输入。
- **超时兜底**：即便远程无响应、连接没断，`fetch` 或 `push` 超过 `--timeout`（默认 30s）也会被中止，该仓库标记为超时并跳过，其他仓库照常进行。

超时的仓库会在状态表最上方单独归为一组：

```
--- fetch 超时,已跳过(可调大 --timeout 重试) ---
slow-repo                      main         -                  -                    fetch origin 超时(>30s),已跳过
```

处理办法：

1. **网络慢或仓库大**：调大超时，例如 `--timeout 120`。
2. **想更快看到结果**：调小超时快速筛出卡住的仓库，例如 `--timeout 10`，之后单独处理它们。
3. **怀疑是并发或某个仓库本身的问题**：用 `--workers 0` 关闭多线程，改为单线程串行，逐个仓库跑更容易定位是哪一个、卡在哪一步。
4. **确认是凭证问题**：单独进那个仓库手动跑一次 `git fetch`，把凭证配好（如配置 SSH key 或凭证管理器）后再重跑。

## 建议用法

1. 第一次对一批仓库操作时，先加 `--dry-run` 看清楚会执行什么。
2. 日常拉取用默认安全模式即可，脏工作区/分叉的仓库会被跳过、留给你手动处理。
3. 确认某批仓库可以放心自动合并时，再加 `--force`，并留意结果里列出的"跳过的冲突文件"。
